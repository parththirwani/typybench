# Error-to-context retrieval experiment

## Question and scope

Can one cross-file definition, selected from a coding repository in response to a `mypy` error, improve a language model's one-shot type-annotation repair? Compare an error-only prompt with the same prompt plus the selected definition. This is a paired pilot, not a claim about general performance across TypyBench.

Use the TypyBench `flask` repository in the dev split. Do not use the test split to tune prompts, selection rules, or retrieval. The proposed cap is 20 eligible diagnostics, chosen before either correction arm runs. If fewer qualify, report the actual count. Do not add another repository without recording that decision before inspecting correction outcomes.

### Scope decision, 2026-10-19

The initial Flask pilot yielded three eligible diagnostics from one `_render(app: App)` annotation, so they are one repair root cause, not three independent cases. A separate 30-call `app.py` baseline added annotations but yielded no new eligible errors. Before inspecting any outcomes on another repository, expand exploratory development to `typer`, which `split.json` places in the dev split and which has a compact 15-file `typer/` package. Use only its `repo_without_types` tree for prompts and retrieval. Keep the same model, fixed arms, annotation-only edit policy, and no test-split tuning. Record Typer results separately from Flask; do not pool correlated diagnostics or call a one-repository effect general.

### Typer repair-site protocol, before correction calls

Typer's baseline generated cross-file `arg-type` errors at call sites where an annotation-only edit on the call line is impossible. For this exploratory Typer variant, resolve the keyword argument named in the diagnostic to its predicted constructor/function parameter annotation in the frozen baseline. Both arms receive that same numbered repair-site line and must edit only that line, in its own file. Arm B additionally receives the corresponding untyped definition from `repo_without_types`; Arm A does not. Deduplicate diagnostics that map to the same `(repair file, repair line, parameter)` before running either arm. Exclude cases with no unique annotated parameter. This changes the edit location, not the annotation-only constraint or the isolation of each case. Keep these results separate from the original Flask same-file protocol and label them exploratory.

### Second dev cohort, before its correction calls

The Typer variant yielded two repair sites, one shared success and one shared invalid long-line patch, with no observed B-only outcome. Add `pre-commit` from the dev split as a separate exploratory cohort. Use the same cross-file named-argument repair-site selection, model, arms, source isolation, and annotation-only validation. Select and freeze its cases before running any correction calls. Report each repository separately; any pooled analysis must account for within-repository and shared-root-cause dependence.

Before pre-commit correction calls, extend the repair-site selector to positional `arg-type` diagnostics: map the reported one-based argument number to the corresponding annotated positional parameter in the predicted cross-file function or constructor (excluding `self`/`cls`). Keep only unique, single-line parameter sites. This is a mechanical extension of the Typer named-argument protocol and is fixed before inspecting pre-commit treatment outcomes.

## Implementation contract

Create `experiments/error_to_context/` code and tests without changing the published TypyBench metrics. Expose commands for `preflight`, `build-baseline`, `select-cases`, `run-paired`, and `summarize`, or equivalent documented entry points. Every command should support `--dry-run`; dry-run must make no API calls and must not overwrite an existing run.

1. **Preflight.** Check the data paths, dev split, virtual environment, `mypy` version, model setting, and writable output path. Check only whether `CODEMATE_API_KEY` is set, never print it. Reject an output path inside `original_repo`. A live API compatibility probe is optional and must be explicitly requested, because the endpoint's exact supported parameters have not been verified.
2. **Cloud client.** Send chat-completion requests to the configured endpoint. Use fixed prompts and fixed supported generation settings for both arms. Record response ID, latency, reported usage, status, and any retry. If the endpoint does not provide token usage, record `null`; do not invent billed cost. Treat malformed or truncated responses as failures, not successful repairs. Add a mock client for deterministic tests.
3. **Shared baseline.** Copy `repo_without_types` to a run directory. Ask the model to add annotations under a fixed, documented unit of work, such as one function or file per request. Do not change executable statements. Validate proposed edits with AST parsing and an annotation-only diff check. Freeze one completed predicted-repository snapshot and hash its files before selecting cases. This stage must not read `original_repo`.
4. **Diagnostics and selection.** Run the pinned `mypy` against the frozen snapshot with a recorded command, working directory, configuration, and environment. Parse stable error codes and locations. Consider `arg-type`, `assignment`, and `attr-defined`. Define a case ID from file, span, error code, and a normalized message. Exclude an error if its referenced symbol cannot be resolved unambiguously to a cross-file function, class, or type definition in `repo_without_types`; log the exclusion reason. Sort by path, line, column, and code, then freeze the first 20 eligible case IDs. If the model's initial annotations produce no eligible cases, stop and report that result rather than fabricating examples.
5. **Definition retrieval.** Resolve imports and symbols with AST-based indexing. Retrieve at most one definition and 300 tokens, with a deterministic truncation rule. If an exact tokenizer for the requested model is unavailable, use a fixed 1,200-character cap, label it as an approximation, and report the actual API input-token usage when returned. Record source path, line span, symbol, and a content hash. Never retrieve from `original_repo`, generated predictions, earlier model responses, or any test-set repository. Reject ambiguous resolution rather than falling back to text search.
6. **Paired correction.** For each case, create two independent copies of the same frozen baseline. Arm A receives the exact `mypy` diagnostic, affected line, and fixed local window. Arm B receives identical material plus the retrieved definition. Use the same model, edit format, and supported generation settings. Request one minimal annotation edit per arm. Disallow imports, executable-code changes, file creation, and changes outside the target file. Parse and validate edits before applying them. Record invalid output as a failed attempt; do not silently repair it. Run each case in isolation so one correction cannot alter another case's starting state.
7. **Results.** Save one structured row per case and arm, including case ID, baseline hash, prompt hash, retrieved source hash for B, model response ID, edit validity, diagnostic counts, target outcome, usage, latency, and error or exclusion reason. Save enough redacted artifacts to reproduce decisions without saving the key. Make the summarizer read saved artifacts only, so it never causes new API calls.

Unit tests should cover import aliases, relative imports, same-name symbols in multiple modules, unresolved symbols, multi-line definitions, 300-token truncation, invalid patches, executable-code edits, diagnostic parsing, and credential redaction. Add a test that fails if a prompt or retrieval path enters `original_repo`.

## Evaluation rules

The comparison unit is a **case**, not an entire repository. Both arms must start from the same baseline hash. Select and freeze cases before running either arm. If an arm errors, count it as an unsuccessful attempt and report failures separately; do not remove only the failed arm from the paired sample.

Primary metric: **clean correction rate**. A case succeeds if the target diagnostic is absent after the edit and the total `mypy` error count does not exceed the same case's baseline count. Because line numbers can move, match the target by file, code, normalized message, and implicated symbol where possible; review ambiguous matches manually and mark them unresolved rather than assuming success. This metric is stricter than target-error disappearance alone, but it does not prove semantic correctness.

Report a paired table: both succeed, A only, B only, neither. Report each arm's numerator and denominator, the paired difference in percentage points, and raw per-case outcomes. Secondary measures are target disappearance, change in total `mypy` errors, invalid-edit rate, retrieved-definition resolution rate, API calls, reported input and output tokens, and latency. Review every B-only win and A-only win with the saved prompt and diff. Note that B uses more context than A; this pilot tests the value of that specific added definition, not a token-matched control.

The official TypyBench scorer reports repository-level TypeSim and TypeCheck. Use it only as a secondary check on any complete prediction repository that the runner produces. Do not call a per-case `mypy` result a TypyBench TypeCheck score, and do not average scores from unrelated isolated case copies as if they were one repository result. If making aggregate A/B repositories, apply only non-overlapping valid edits under a documented order, rerun `mypy`, and label those scores exploratory because edits may interact.

For the official scorer, the README examples omit `--data-path`. Build only the `flask` image with `python run.py --data-path /home/too_geeky/research/typybenchdata --build --repo flask --num-workers 1`, then evaluate a prediction root whose immediate child is `flask` using the same `--data-path` plus `--pred-path` and `--repo flask`. The Docker build may be slow because its Dockerfile installs multiple Python versions. Record any build or environment failure separately from model quality.

## Acceptance gates

1. `preflight --dry-run` passes without showing a credential or making a network request.
2. Unit tests pass, including the reference-data isolation and annotation-only edit tests.
3. A three-case smoke test on a small fixture or bounded Flask subset produces one frozen baseline, a frozen case list, two independent correction attempts per case, and a results table within 12 API calls. The two arms' baseline hashes match in every row.
4. The summarizer recomputes metrics from saved rows without API calls. A deliberate missing response or invalid patch remains visible as a failed attempt.
5. Only after those gates pass, run the capped pilot and, if feasible, the official scorer. Report deviations from this spec before interpreting results.
