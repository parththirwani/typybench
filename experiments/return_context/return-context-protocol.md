# Cross-file return-type retrieval (separate exploratory study)

This study is distinct from `error_to_context`'s mypy-repair arms. The repair pilot found three independent sites and no B-only correction; its diagnostics usually exposed both actual and expected types. The new question is whether retrieving an imported function's *untyped body* improves prediction of that function's return annotation from a caller's evidence. This tests a concrete read-memory action and its token cost, not mypy repair or official TypyBench TypeCheck.

Protocol fixed before cloud predictions or typed-reference inspection:

1. Use only the `flask`, `typer`, and `pre-commit` dev-split `repo_without_types` trees for selection and prompts. No test-split files. Search top-level caller functions for calls to a uniquely resolved, top-level function in another source file. The callee must have no return annotation in stripped code. Exclude ambiguous imports and definitions. Keep one caller per callee, selected by SHA-256 ranking of the caller identity; cap the corpus at 60 unique callees by SHA-256 ranking of case ID. Selection never reads `original_repo`.
2. Arm A receives the caller function (up to 2,400 characters), relevant import, and the callee name, and predicts the callee return type. Arm B receives exactly the same plus at most 1,200 characters of the callee's untyped definition. Both use `gpt-5.4-mini`, temperature zero, the same output format `{"return_type": "..."}`, one attempt, and no tools/local model. Record all prompt hashes, response IDs, usage, validity, and latency. Both arms are paired by callee.
3. Freeze selected cases and both arms' predictions before opening the typed reference. Then score against the corresponding top-level function's return annotation in `original_repo`. If the reference has no unique annotated function, mark the case unevaluable without dropping it silently. Primary metric: exact AST-normalized return-type match among evaluable held-out cases. Invalid output counts as incorrect. Report a paired table, coverage, and an exact two-sided McNemar p-value. Secondary: reported input/output tokens and latency. Do not claim official TypeSim or TypeCheck from this function-level score.
4. The first six ranked cases are a format smoke test. If the format fails, repair the pipeline before evaluating the remaining cases; never include those six in a significance claim. The remaining up to 54 cases form the held-out set. A research report requires at least 20 evaluable held-out cases, a positive B–A difference, and McNemar p < 0.05. Otherwise preserve run artifacts and report the limitation without claiming retrieval efficacy.

This study is deliberately simple: B has more task-relevant source than A and uses more tokens. It does not test a learned cost-aware trigger. Only if there is reliable benefit on some cases and no benefit on others can a later trigger study use *pre-retrieval* signals to predict when the extra read is worth its cost.
